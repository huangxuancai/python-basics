========================================================================================
Cookie / Session / Token 认证靶场 · http://127.0.0.1:8766
========================================================================================

【第 1 步】Cookie 只是「信封」：服务器下发，客户端之后自动回传
----------------------------------------------------------------------------------------
> GET /pref/set
< 200  Set-Cookie 原文: theme=dark; Path=/; SameSite=Lax
> GET /pref/show   （客户端没写任何代码，cookie 自动带上）
< 200  {'theme_from_cookie': 'dark'}
观察：Cookie 自己不会认证。它只是把数据从服务器搬到客户端，再搬回来。

【第 2 步】Session：登录后服务端建会话，客户端只拿一个 sid
----------------------------------------------------------------------------------------
> GET  /login?user=admin&pwd=Passw0rd
< 200  Set-Cookie: SID=U2aTH_huaBlQgd6Gj_cszIRG; HttpOnly; Path=/; SameSite=Lax
   客户端只拿到 sid = U2aTH_huaBlQgd6Gj_cszIRG
   服务端登记表里有 {'uid': 1, 'user': 'admin', 'role': 'user'}
> GET  /me   （自动带 Cookie: SID=U2aTH_huaBlQgd6Gj_cszIRG）
< 200  {'ok': True, 'source': '服务端会话表', 'user': {'uid': 1, 'user': 'admin', 'role': 'user'}}
观察：服务器拿 sid 去会话表里查，查到才知道你是谁 → 这就是「有状态」。

【第 3 步】Session 能主动失效：登出后同一 sid 立刻失效
----------------------------------------------------------------------------------------
> GET  /logout
< 200  {'ok': True, 'msg': '已登出', 'server_session_deleted': True, 'session_count': 0}
> GET  /me   （手动把旧 sid=U2aTH_huaBlQgd6Gj_cszIRG 塞回 cookie，模拟盗号者）
< 401  {'ok': False, 'msg': '未登录或会话已失效（服务端查不到这个 sid）'}
观察：服务端删了那条会话，旧 sid 立刻废掉。这是 Session 的最大优势。

【第 4 步】JWT：服务器签一个自包含 token，自己不存任何东西
----------------------------------------------------------------------------------------
> GET  /jwt-login?user=admin&pwd=Passw0rd
< 200  token = eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJ1aWQiOjEsInVzZXIiOiJ...（共 155 字符）
   服务器当前会话表条数: 0（JWT 登录不产生会话）
> GET  /jwt-me   Authorization: Bearer <token>
< 200  {'ok': True, 'source': '签名验证（没查任何表）', 'payload': {'uid': 1, 'user': 'admin', 'role': 'user', 'exp': 1795852608}}
观察：服务器没查任何表，验签就把你算出来了 → 这就是「无状态」。

【第 5 步】JWT 的 payload 用 Base64 编码，谁都能解开看
----------------------------------------------------------------------------------------
   原始 payload（Base64）: eyJ1aWQiOjEsInVzZXIiOiJhZG1pbiIsInJvbGUiOiJ1c2VyIiwiZXhwIjoxNzk1ODUyNjA4fQ
   解码后: {"uid": 1, "user": "admin", "role": "user", "exp": 1795852608}
   header 解码: {'alg': 'HS256', 'typ': 'JWT'}
观察：uid / user / role / exp 全明文。Base64 是编码不是加密。
     → 推论：绝不能在 payload 里放密码、身份证号、手机号

【第 6 步】篡改 payload 的 role → 签名对不上 → 401
----------------------------------------------------------------------------------------
   篡改后 payload: {"uid": 1, "user": "admin", "role": "admin", "exp": 1795852608}
< 401  {'ok': False, 'msg': '签名不一致（payload 被改过，或不是本服务器的密钥签的）'}
观察：防篡改靠的是签名（HMAC-SHA256 + 服务器密钥），不是「看不见」。
     想自己重算签名？没有密钥算不出来。

【第 7 步】⭐ 改密码后：Session 立刻失效，JWT 仍然有效（漏洞现场）
----------------------------------------------------------------------------------------
   先重新登录：新 sid = GElEzK_weh6h1MvfS485lEvs，新 token 沿用第 4 步那个
   改密前 /me（Session）    → 200
> GET  /change-password?user=admin&new=NewPass!2026
< 200  {'ok': True, 'msg': '密码已修改', 'sessions_killed': 1, 'note': '服务端能清会话，但已签发的 JWT 它记不住'}
   改密后 /me（Session）    → 401  未登录或会话已失效（服务端查不到这个 sid）
   改密后 /jwt-me（JWT）    → 200  {'uid': 1, 'user': 'admin', 'role': 'user', 'exp': 1795852608}

   ⚠️ 同一个用户、同一次密码修改：
      Session 手里的凭证立刻作废（服务端删了会话）
      JWT 手里的旧 token 依然能访问（服务器没有作废它的手段）
   → 这就是'JWT 无法主动登出'的真实后果。工程解法：
      ① 黑名单（作废列表）② 短有效期 access + 可撤销 refresh ③ token 带密码版本号

【第 8 步】三种方案对照（背这四行就够）
----------------------------------------------------------------------------------------
              Cookie            Session             Token(JWT)
本质            传输容器              服务端会话               自包含凭证
数据存哪          客户端               服务端                 客户端(payload)
状态性           —                 有状态                 无状态
能否主动失效      删 cookie          删会话 ✅               只能等过期 ❌
分布式           —                 要共享(Redis)          天然支持 ✅

面试三句话：
  1) HTTP 无状态，登录就是在无状态协议上造'我记得你'的假象；Cookie 是信封不是方案
  2) Session 有状态——服务端存会话，能主动失效，但要共享、占内存
  3) JWT 无状态——签名自包含，天然分布式，但无法主动失效、payload 明文可读
