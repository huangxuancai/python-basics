# 2026-11-25（W4 Day1 · HTTP 请求响应结构）


**做了什么**：`day13_practice.py`（AI 建好，我读输出指认四部分）+ `http报文解剖.txt` 存档；F12 抓到真实 GET（B站二维码轮询）和 POST（数盟风控上报）并找到 Request Payload；手绘请求/响应两张结构图；录音 2 分钟自检通过

**卡住的地方**：

```
1. 以为"请求对应POST、响应对应GET" → 概念混淆：请求/响应是方向，GET/POST是方法，
   两个维度不搭界。怎么问都有一答，答里只有状态码没有方法。
   用 weather_cli.py 验证：requests.get() 的 r 就是 GET 的响应，W2 天天在用
2. F12 的 General 栏看不出 GET/POST 区别 → 区别不在摘要卡片在"行李"：
   GET 参数挂 URL（B站那条把整个JSON编码进query，%22就是引号），
   POST 数据在 body（Payload 标签），GET 没有 Request Body 这一块
3. 以为 Content-Type 可信 → 一天撞见两次声明与实际不符：
   wttr.in 声明 text/plain 实际返回 JSON（r.json()照样成功）；
   数盟风控声明 text/plain; charset=utf-8 实际是二进制指纹数据（DevTools按UTF-8硬解出乱码）
4. 谁在请求谁在响应绕不清 → 铁律：谁先开口谁是客户端。POST"送数据"也是请求，
   因为本义是"请你处理"；服务器只答不问。自测3/3过
5. day13 首跑 GBK 编码崩（UnicodeEncodeError）→ Windows 控制台老坑，
   sys.stdout.reconfigure(encoding="utf-8") 修复，脚本里留了注释
```

**学到的规律**：

```
- 报文四部分口诀："一行、几行、空行、一坨"；响应与请求对称，只把请求行换成状态行
- r 是收到的信（响应），r.request 是寄出去的信的底单（PreparedRequest）
- Content-Type 是服务器的自我声明不是保证书，接口断言要验 body 实际格式，不能只信头
- "POST 比 GET 安全"是错的：两者 HTTP 层都明文，POST 只是把数据从 URL 挪进 body，
   藏 ≠ 加密，安全靠 HTTPS——这正是占位用例 TC-LOGIN-W4-01 的原理
- 幂等 = 发1次和发N次效果一样；POST 非幂等 → 重复提交订单是接口必测点
- 一次页面刷新会向十几个不同域名发请求，看 Request URL 域名才知道在跟谁说话（Day6 基本功）
```

**面试能用**：

- "HTTP 请求分请求行/头/空行/体四部分，响应把请求行换成状态行。GET 幂等可缓存、POST 非幂等，所以接口测试必测重复提交。两者都是明文，不存在 POST 更安全，密码类必须 POST+HTTPS"
- "我抓包实测过 Content-Type 声明与实际不符的两个案例：API 声明 text/plain 返回 JSON、风控接口声明文本实为二进制。所以我的断言不依赖 Content-Type 单一字段，会校验响应体实际可解析性和结构"
