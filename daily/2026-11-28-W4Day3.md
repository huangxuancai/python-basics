**卡住的地方**：

```
1. ⭐ 第 4 题答不出来：百万用户在线用 Session 有什么麻烦 → 我只想到"内存会崩"，
   完全漏了更致命的一条：多机部署会话不共享。
   → 补上的答案分两层：
     ① 内存：100 万在线 × 每会话 ~1KB ≈ 1GB，还得算扩容冗余
     ② 分布式（更致命）：登录落在 A 机，下次请求被负载均衡打到 B 机，
        B 机查不到会话 → 用户莫名其妙被踢下线。这是"老是掉登录"的经典根因
   解法三层（从土到彻底）：
     a. 粘性会话：负载均衡按 cookie 把同一用户钉死在一台机 —— 简单，但那台挂了用户全掉
     b. Redis 集中存会话（主流）：所有机器共享，加机器无感，TTL 自动过期
     c. 换无状态 JWT：干脆不存 —— 但换来"不能主动失效"，正好回到今天的核心矛盾
   一句话：Session 的扩展性问题本质是"状态放在了单机上"，
   解法要么把状态搬出去（Redis），要么把状态消灭（JWT）
2. Q3 表述需要精修："靠签名的密钥"方向对，但要说清保的是"完整性"不是"机密性"——
   签名防的是"改不了"，不是"看不见"。payload 依然明文。
3. 画 JWT 时序图时卡了一下："服务器不存东西怎么验证" —— 想通关键：签名是用服务器
   密钥算的，服务器只需重算一遍比对，不需要记住谁登录过
```

**学到的规律**：

```
- Cookie 是信封不是信：Session 和 JWT 都是信，都能装在信封里寄
- Session vs JWT 的核心不是"谁更先进"，是"状态放哪"：放服务端=能撤销但要共享，
  放客户端=天然分布式但不能撤销。所有工程方案都是在补这个取舍的窟窿
- Base64 是编码不是加密：JWT payload 谁都能解开，所以绝不放密码/身份证/手机号；
  安全靠签名（完整性），不靠"看不见"（机密性）
- 靶场第 7 步最有价值：同一个用户同一次改密码，Session 401 而 JWT 仍 200。
  这就是"改密码后旧 token 是否仍有效"这条用例要抓的缺陷，很多系统真有
- 靶场第 6 步：改 payload 的 role 但签名不动 → 401。防篡改是算出来的，不是藏出来的
```

**面试能用**：

- "HTTP 是无状态的，登录的本质是在无状态协议上造'我记得你'的假象。Cookie 不是方案是容器，Session 和 JWT 都靠它传"
- "Session 有状态：服务端存会话，能主动失效，但多机要共享（Redis）、百万用户占内存、单机状态是扩展性瓶颈。JWT 无状态：验签即认证，天然分布式，但无法主动失效、payload 明文"
- "JWT 无法登出的三种补法：黑名单、短有效期 access + 可撤销 refresh（OAuth2 主流做法）、token 带密码版本号。我在靶场里实测过改密码后旧 token 仍能访问"
- "Session 的分布式问题我理解成：状态放在了单机上。解法要么把状态搬出去（Redis），要么消灭状态（JWT）"
